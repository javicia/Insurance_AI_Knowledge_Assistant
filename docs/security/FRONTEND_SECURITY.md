# Frontend Security (FASE 32)

Status: living document, describes the real implementation - the audit sweep below was run
against the actual `frontend/src` tree, not assumed.

## 1. Audit sweep results

Grep-based sweep of `frontend/src` for the categories the brief calls out:

| Check | Result |
|---|---|
| `innerHTML`, `bypassSecurityTrust*`, `eval(`, `new Function(` | **None found** - Angular's own template binding/sanitization is relied on exclusively, never bypassed |
| Hardcoded `password`/`apiKey`/`client_secret` string literals | **None found** |
| `localStorage` usage | **None** - `chat-session.service.ts` has a comment explicitly documenting the decision *not* to persist conversation state there (refreshing starts a new session - correct for a tool that may surface PII copied from source documents) |
| `sessionStorage` (application code) | **None directly** - see section 2 for what `angular-oauth2-oidc` itself does |
| `console.log`/`console.debug`/`console.warn` | **None** - the only `console.*` call in the entire tree is `console.error` in `main.ts`'s bootstrap failure handler (the one place a startup failure has nowhere else to report to) |
| Open redirects | **None** - the only redirect-capable code is `AuthService.login()`/`logout()`, both delegating entirely to `angular-oauth2-oidc`'s own Authorization Code Flow redirect, which validates the redirect URI against the Keycloak client's registered `redirectUris` (`infra/keycloak/realm-export.json`) - never a client-controlled URL |
| Source map exposure | Production builds use Angular's default (`sourceMap: false` in the `production` build configuration in `angular.json`) - no `.map` files are shipped |

## 2. Token storage - `sessionStorage`, not `localStorage`

`angular-oauth2-oidc` (FASE 18) is not given a custom `OAuthStorage` provider, so it falls back to
its own documented default: the browser's `sessionStorage`. This is a deliberate, informed choice,
not an oversight:

- **Why not `localStorage`**: tokens would persist across browser restarts/tab closes, widening
  the window an XSS payload (were one ever to exist despite section 1's clean sweep) could
  exfiltrate a still-valid token.
- **Why not an HttpOnly cookie (BFF pattern)**: that pattern requires the token exchange to happen
  server-side (a Backend-for-Frontend), which is a materially different architecture than "pure
  SPA + independent API Gateway" this program's brief mandates (`frontend -> gateway -> backend`,
  frontend never holding server-side session state). Documented here as a real architectural
  tradeoff, not hidden.
- **Residual risk**: `sessionStorage` is still readable by any JavaScript running in the page's
  origin - a genuine XSS vulnerability would still be able to steal a token. This is why section 1's
  clean sweep (no `innerHTML`, no sanitizer bypass, no `eval`) is the primary defense, not the
  storage location - CSP (section 3) is the second layer.

## 3. Security headers

Set in `frontend/nginx.conf` (static headers) and `frontend/docker-entrypoint.sh` (the one
runtime-generated header, CSP - see below for why):

| Header | Value | Purpose |
|---|---|---|
| `X-Content-Type-Options` | `nosniff` | Prevents MIME-sniffing a response away from its declared `Content-Type` |
| `X-Frame-Options` | `DENY` | No framing - this app is never meant to be embedded |
| `Referrer-Policy` | `strict-origin-when-cross-origin` | Doesn't leak full URLs (which could contain sensitive query params) to third-party origins |
| `Permissions-Policy` | `geolocation=(), microphone=(), camera=()` | This app uses none of these - explicitly denied rather than left to browser defaults |
| `Content-Security-Policy` | see below | Restricts script/style/connect/frame origins |

### Content-Security-Policy - generated at container startup, not hardcoded

```
default-src 'self';
script-src 'self';
style-src 'self' 'unsafe-inline' https://fonts.googleapis.com;
font-src 'self' https://fonts.gstatic.com;
img-src 'self' data:;
connect-src 'self' <PUBLIC_API_BASE_URL> <PUBLIC_OIDC_ISSUER>;
frame-ancestors 'none';
base-uri 'self';
form-action 'self';
```

- **`connect-src` includes the real, deployment-specific `PUBLIC_API_BASE_URL`/`PUBLIC_OIDC_ISSUER`**,
  not a hardcoded value - generated by `docker-entrypoint.sh` at container startup into
  `/etc/nginx/conf.d/csp-header.conf`, the same runtime-configuration principle already
  established for `env.js` (FASE 16/18): one built image, deployable against any environment's
  gateway/Keycloak URL, CSP included.
- **`script-src 'self'` only** - no `'unsafe-eval'`, no `'unsafe-inline'` for scripts. This is a
  production, AOT-compiled Angular build (`ng build`'s default), which does not require either.
- **`style-src`/`font-src` allow Google Fonts** (`https://fonts.googleapis.com`,
  `https://fonts.gstatic.com`) - the one third-party origin `index.html` actually loads (Inter +
  Material Symbols Rounded, see `docs/frontend/UI_GUIDELINES.md`). `'unsafe-inline'` for styles is
  a real, evaluated exception (Angular Material injects some styles at runtime) - not blanket
  permissiveness; `script-src` has no equivalent exception.

**FASE 26: this CSP is now verified in a real browser - and it was broken.** It was previously
checked only with `curl -I`, confirming the header was present and correctly substituted. That
turned out to say nothing about whether it was *correct*. A real Chromium run (see
`docs/testing/E2E_PLAYWRIGHT.md`) surfaced two defects a header inspection could never find:

1. `script-src 'self'` blocked the inline `onload` handler that Angular's critical-CSS inlining
   emits, so the deferred stylesheet never activated. Fixed by disabling `inlineCritical` in the
   build - deliberately **not** by adding `'unsafe-inline'`/`'unsafe-hashes'`, which would have
   weakened the policy to accommodate the build.
2. `connect-src` listed the OIDC issuer **without a trailing slash**. Under CSP path-matching, a
   source expression whose path does not end in `/` matches that one exact URL and nothing beneath
   it - so `.well-known/openid-configuration` was blocked and **login could never start**. Fixed in
   `docker-entrypoint.sh`, and now guarded by an E2E test asserting the issuer source ends in `/`.

The lesson is recorded rather than quietly patched: a CSP can only be validated by an engine that
enforces it.

## 4. Where responsibility for the WAF vs. the frontend divides

`docs/adr/ADR-016-WAF-EDGE.md` documents this from the WAF's side; restated here from the
frontend's: XSS defense is primarily Angular's own template sanitization (section 1) plus this
document's CSP, never the WAF - a WAF sitting in front of a genuinely vulnerable frontend would
only ever be a secondary, imperfect filter, not a substitute for the frontend not having the
vulnerability in the first place.
